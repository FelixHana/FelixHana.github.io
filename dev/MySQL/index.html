    MySQL

    执行流程¶

    Server 层¶

    连接器、（server 缓存）、解析器、预处理器、优化器、执行器

    连接器¶

    本质上是进程间通信
    - 主要采用 TCP/IP ，参数 -P 指定端口号
    （Windows：命名管道 共享内存）（类 Unix：套接字）
    - 空闲连接的最大空闲时长 wait_timeout
    - 最大连接数 max_connections
    - mysql_reset_connection 函数重置连接

    查询缓存¶

    8.0 后删除
    表更新即失效，命中率低

    解析器¶

    词法、语法分析
    - 解析器只负责检查语法和构建语法树，但是不会查表或者字段存不存在

    预处理器¶

    • 检查表或者字段存在
    • 扩展 * 符号

    优化器¶

    SQL 查询语句制定执行计划，决定使用的索引
    explain 查询的 type、选择的 key
    性能分析

    执行器¶

    根据执行计划执行 SQL 查询语句，从存储引擎读取记录，返回给客户端
    图解 MySQL 执行器

    存储引擎 InnoDB¶

    数据存放在 datadir 目录下
    - db.opt 存储当前数据库的默认字符集和字符校验规则
    - xxx.frm 保存每个表的元数据信息，主要包含表结构定义
    - xxx.ibd 表数据文件
    表空间 — 段 — 区 — 页 — 行
    - 段
    - 索引段：B+ 树的非叶子结点的区
    - 数据段：叶子节点的区
    - 回滚段：回滚数据的区
    - 区
    - 每个区的大小为 1MB，对于 16KB 的页来说，连续的 64 个页会被划为一个区
    - 顺序 I/O：相邻页的物理位置也相邻

    InnoDB 行格式¶

    Redundant、Compact、Dynamic 和 Compressed
    5.7 之后，默认使用 Dynamic

    变长字段长度列表（非必须）¶

    • 占用的字节数按照列的顺序逆序存放，提高 CPU Cache 的命中率
    • 可变字段允许存储的最大字节数（ M×W ）超过255字节且真实存储的字节数（ L ） 超过127字节，则使用2个字节，否则使用1个字节
    • NULL 值的不存

    NULL 值列表（非必须）¶

    • 逆序存放
    • 高位补齐整字节

    记录头信息¶

    • 固定 5 字节 = 40 bit
    • 删除位、非叶子节点最小记录、Slot 记录数、页中位置信息、类型、下一条记录相对位置
    • 页中位置信息 heap_no 默认最小/最大记录 为 0 和 1 其他完整记录按主键排序
    • 类型 record_type 0 普通， 1 B+树非叶节点， 2 最小记录， 3 最大记录
    • 下一条记录指针 next_record 从当前记录的真实数据到下一条记录真实数据的地址偏移量（单链表）

    真实数据¶

    • 隐藏列：默认主键 row_id（未定义 Primary & Unique）、事务 id trx_id、
      • 上一个版本指针 roll_pointer （MVCC）insert undo 标记、回滚段编号、undo log页面 页号、页面偏移量
    • CHAR(M)：采用定长字符集时，占用的字节数不会被加到变长字段长度列表，而如果采用变长字符集时，占用的字节数也会被加到变长字段长度列表

    行溢出数据¶

    VARCHAR(n)¶

    除了 TEXT、BLOBs 这种大对象类型之外，其他所有的列占用的字节长度加起来不能超过 65535 个字节，包含变长长度和 NULL
    VARCHAR(n) 包含：真实数据、占用字节长度值、NULL 值标识
    n 最大值 = (65535 - 2 字节长度值 - 1 NULL 标识) / 字符集一个字符最多字节数

    溢出处理¶

    页的大小一般是 16KB = 16384 字节，136 + 2 记录 × (27 + n) > 16384，一个列中存储的数据不大于 8098 个字节，不会发生行溢出
    行溢出时，真实数据处只会保存该列的一部分数据，而把剩余的数据放在溢出页中，用 20 字节存储指向溢出页

    InnoDB 页结构¶

    Page Directory¶

    • 将记录分组后，每组的最后一条记录的地址偏移量存到页目录，称为槽 Slot
    • 每个组的最后一条记录头信息中的 n_owned 属性表示该组记录共有多少条
    • 最小记录所在分组只有 1 条记录， 最大记录所在分组在 1~8 条之间，剩下的分组在 4~8 条之间
    • 插入后大于 8 即分裂成两个分组，新增 Slot
    • 查找：二分法确定 Slot 后利用 next 指针遍历

    File Header¶


    - 各数据页利用 prev next 构成双向链表

    File Trailer¶

    校验和 + LSN

    索引¶

    • 高效获取记录的数据结构
    • 复用用户记录的结构，索引记录用 record_type 区分
    • 实际用户记录存放在B+树最底层节点
    分类 含义 特点
    聚簇索引 数据存储与索引放到一起，叶子节点保留行数据 有且仅有一个
    二级索引 数据与索引分开存储，叶子节点关联的是对应主键 可以有多个
    • 联合索引（包含多个列的二级索引）记录先按列 1 排序，再按列 2 排序
    • 根节点不会移动，用户记录先插入根节点，空间用尽后复制到新的数据页，根节点升级为目录
    • 二级索引目录项记录包含主键值，用于区分指向的数据页

    索引失效¶

    • 最左前缀法则
    • 范围查询<>右侧列索引失效，尽量使用<=/>=
    • 不要对索引列上进行运算操作，要单独出现
    • 字符串不加引号索引失效
    • 模糊查询：头部模糊匹配索引失效，尾部模糊匹配索引不会失效
    • 用 or 分割开的条件需要前后都有索引
    • 数据分布影响：评估索引和全表查找的速度
    • 索引排序
      • 按照联合索引顺序
      • 不能 ASC DESC 混用
      • Where 出现非排序用到的索引列
      • 排序列不在一个索引里

    索引设计原则¶

    • 常作为条件where、排序order by、分组group by操作的字段
    • 尽量使用覆盖索引，减少 select *
      • using index condition 需要回表查询
      • using where; using index 所需数据在索引列都能找到，无需回表
    • 为基数大的列建立索引
    • 数据类型尽量小
    • 字段类型为字符串（varchar，text），只使用一部分前缀创建索引 长度n根据索引的选择性确定
      选择性：不重复的索引值（基数）和数据表记录总数的比值
    • 控制索引数量，考虑增删改时维护索引的代价
    • 使用NOT NULL约束，利于优化器确定使用的索引

    索引分类¶

    类型 含义 特点 关键字
    主键索引 针对主键创建的索引 只能有一个 PRIMARY
    唯一索引 避免数据列值重复 多个 UNIQUE
    常规索引 定位特定数据 多个
    全文索引 查找文本关键词 多个 FULLTEXT

    性能分析¶

    • 执行频率 show global status like 'Com_______' 增删改查次数
    • 慢查询日志
      • my.cnf 中 slow_query_log=1 long_query_time=秒数
      • log 在 /var/lib/mysql/localhost-slow.log
    • profile
      • 打开 set profiling = 1
      • show profiles
      • show profiles for query ? 单条语句具体耗时信息
    • explain/desc select...
      • id 字段相同执行顺序从上到下，id不同值越大越先执行
      • select_type SIMPLE/PRIMARY/UNION/SUBQUERY...
      • type 连接类型 性能由好到差 NULL/system/const(主键、唯一索引)/eq_ref/ref(非唯一索引)/range/index/all
      • Key_len 索引字段可能最大长度
      • rows 必须查询行数估计值
      • filtered 结果行数占需读取行数百分比

    InnoDB 表空间¶

    Extent 区¶

    • 是连续的 64 个 16 KB 页 = 1MB
    • 256 个 extent 为一组
    • 第一个组前三个页面
      • FSP_HDR 登记整体属性和所有的区，表空间唯一
      • IBUF_BITMAP 存储本组所有的区的所有页面关于 INSERT BUFFER 的信息
      • INODE
    • 其余各组前两个页面
      • XDES extent descriptor 登记本组 256 个区的属性
      • IBUF_BITMAP
    • 区的分类 (前三个直属于表空间)
      • FREE 空闲的区
      • FREE_FRAG 有剩余空间的碎片区
      • FULL_FRAG 没有剩余空间的碎片区
      • FSEG 附属于某个段的区

    XDES Entry¶

    • Segment ID 该区所在的段（若分配）
    • List Node 双向链表指针
    • State 区分类
    • Page State Bitmap 每两个 Bit 对应一个页
    • 使用 XDES 管理插入数据的页分配（直属于表空间）
      • 类型 FREE / FREE_FRAG / FULL_FRAG 的 XDES 各自形成链表
      • 段数据较少时先找 FREE_FRAG 若没有 找 FREE
      • 段中数据占 32 页后申请完整的区插入数据
    • XDES 管理段中的区（附属于某个段）
      • FREE 链表：同一个段中，所有页面都是空闲的区对应的 XDES
      • NOT_FULL 链表：同一个段中，仍有空闲空间的区对应的 XDES
      • FULL 链表：同一个段中，没有空闲空间的区对应的 XDES
    • 每个索引对应两个段，每个段都会维护上述 3 个链表
    • 所有链表基节点在表空间位置固定，维护链表节点数量和头尾节点

    Segment 段¶

    • Segment 是逻辑概念，由零散的页面和一些完整的区组成
    • 为每个段定义一个 INODE Entry
      • NOT_FULL_N_USED：NOT FULL 链表中已经使用了多少个页面
      • Fragment Array Entry：每个表示一个零散页面的页号
    • Fragment 指该段零散页面页号

    表空间组织¶

    各类型页面的详细情况，如何组织成一个完整的表空间

    FSP_HDR 类型¶

    • 表空间的第一个页
    • 存储表空间一些整体属性，第一个组内256个区的对应的 XDES Entry
    File Space Header¶

    存储表空间整体属性

    - List Base Node for FREE...：直属于表空间的 XDES Entry 链表基地址Extent 区
    - FRAG_N_USED 在 FREE_FRAG 链表中已经使用的页面数量
    - FREE Limit：只有该字段之前的区初始化
    - Next Unused Segment ID：用于创建新段
    - Space Flags：各种表空间属性
    - List Base Node for SEG_INODES_FULL / SEG_INODES_FREE：INODE 页面链表基节点

    XDES Entry(s)¶

    每组的第一个页面中存放 256 个 XDES Entry，对应 256 个 Extents

    XDES 类型¶

    除了第一个组，每组的第一个页面记录有 256 个 XDES Entry
    注意是保存 XDES 的页面，与 FSP_HDR 结构上相似

    INODE 类型¶


    - INODE Entry：大小192B，一页共 85 个
    - List Node for INODE Page List：用于管理 INODE 页面的链表
    - SEG_INODES_FULL / FREE 链表：链表中的 INODE 类型的页面中 没有/还有 空闲空间存储额外的 INODE Entry

    IBUF_BITMAP 类型¶

    与 change buffer 相关

    Segment Header¶

    用于维护叶子/非叶子节点 Segment 的 INODE Entry] 结构对应关系
    Page Header 中定义了 PAGE_BTR_SEG_LEAF 和 PAGE_BTR_SEG_TOP 指向 Segment Header
    只需要在索引的根页面记录

    系统表空间¶

    • 整个MySQL进程只有一个系统表空间 Space ID=0
    • 在 Extent 0 的 0~2 页与独立表空间相同，3~7 页记录系统属性
      • 事务和多版本控制相关信息以及 数据字典 Header
    • 系统表空间的 extent 1 和 2，即 64 ~ 191 这128个页面被称为 Doublewrite buffer

    数据字典¶

    • 内部系统表被称为数据字典，存储用户数据的元数据
    • SYS_TABLES、SYS_COLUMNS、SYS_INDEXES 、SYS_FIELDS 是基本系统表，分别记录了表、列、索引等元信息
    • 系统表空间的一组 一区 第七页 记录了基本系统表的索引的根页面信息
    • 引擎启动时读取 SYS 开头的系统表，填充到 information_schema 供用户查看

    redo log¶

    • 事务提交时将执行过程中的 redo log 刷新到磁盘 满足持久性以及效率要求
    • 好处: 日志占用空间小 且顺序写入磁盘

    redo log 格式¶

    • type 类型
    • space ID 表空间 ID
    • page number 页号
    • data 具体数据 格式取决于类型

    物理日志¶

    • 仅记录偏移量+字节数+具体数据
    • MLOG_1BYTE, MLOG_2BYTE, MLOG_4BYTE, MLOG_8BYTE, MLOG_WRITE_STRING
      • 其中 WRITE_STRING 写入一串数据, 还需要另外记录数据长度

    物理+逻辑日志¶

    • 插入记录涉及到的更改很多，如 Page Directory / Header 中的信息，记录头链表信息等等
    • 为了避免过多的 redo log 设计了各类复杂情况的日志类型
    • 如 MLOG_COMP_REC_INSERT 插入一条使用紧凑行格式的记录
    • 记录必要的参数，通过特定的函数进行恢复操作
    • 目标尽量减小 redo log 的大小

    Mini-Transaction¶

    • 悲观插入：修改多个页，产生多条 redo log，如果不能保证原子性则会引发错误
    • 不可分割的日志
      • 更新 Max Row ID 属性时产生的 redo 日志
      • 聚簇索引对应 B+ 树的页面中插入一条记录时产生的 redo 日志
      • 向某个二级索引对应 B+ 树的页面中插入一条记录时产生的 redo 日志
      • 还有其他的一些对页面的访问操作时产生的 redo 日志
    • 引入 MLOG_MULTI_REC_END 作为一组 redo log 的结尾标记
    • 单条 redo 日志将 type 首个 bit 置为 1 作为标记
    • 每次原子访问称为一个 Mini-Transaction - mtr
    • 一个事务可以包含若干条语句，每一条语句由若干个 mtr 组成，每一个 mtr 可以包含若干条 redo log

    redo log 写入过程¶

    • 通过 mtr 生成的 redo log 存储在 block （同样是 512B 的页）
    • 内存中 redo log buffer 为连续的若干 block
    • 全局变量 buf_free 指示空闲空间
    • 不同 mtr 会交替写入同一个 block

    redo log 文件¶

    • 写入磁盘时机：空间达到阈值、事务提交、后台线程定期、checkpoint、关机...
    • 循环写入日志文件组 0 1 2... n 0 1...
    • 默认 2 个 48MB 的日志文件
    • 每个日志文件前 2048B 即 4 个 512B 的 block 预留给管理信息
      • log file header + 两个 checkpoint

    LSN¶

    • 日志序列号全局变量 初始 8704
    • 代表系统写入的 redo 日志量的总和
    • flushed_to_disk_lsn 实际刷到磁盘的日志量(write_lsn OS缓冲区的日志量, fsync 后才落盘)
    • mtr 结束时将所有修改的页面加入 buffer pool flush 链表
      • 页控制块插入头部并设置oldest_modification 和 newest_modification 的 LSN 值
      • 多次更新同一个页只需修改 newest 值

    checkpoint¶

    • checkpoint_lsn 代表系统中可以被覆盖的 redo 日志总量
    • checkpoint 的步骤
      • 计算最早修改脏页的 oldest 值 产生于该值以前的 redo log 都可以覆盖
      • 写入日志文件的管理信息 checkpoint1 或 2 中(区分奇偶checkpoint_no)

    innodb_flush_log_at_trx_commit¶

    • 系统变量 用于控制 redo log 刷新级别
    • 默认值 1 - 事务提交时需要 redo log 落盘
    • 2 - 事务提交时需要 redo log 写 OS 缓冲区(DB 崩溃而 OS 正常则保证持久性)
    • 0 - 不立即同步 (DB 崩溃则不能保证持久性)

    崩溃恢复¶

    • 起点(时间上早的) checkpoint1/2 中更大的 no 获得 checkpoint_lsn 和 offset
    • 终点(晚的) LOG_BLOCK_HDR_DATA_LEN 未满的即是最后一个 block
    • 恢复过程: 依次扫描 checkpoint_lsn 之后的 redo log
    • 加速恢复的方法
      • 根据 redo log space ID 和 page number 计算 Hash, 链地址法将同一个页面的 redo 链接按序恢复每个页面的所有更改, 避免随机I/O
      • 检查落盘页面 File Header 的 FIL_PAGE_LSN(记录了控制块中的newest_modification, 即最近一次修改) 若大于checkpoint_lsn 则说明已经成功落盘

    undo log¶

    事务 id¶

    • 如果事务对某个表增删改，InnoDB 会分配一个唯一事务 id
      • 读写事务对某个表 / 只读事务对某个临时表第一次增删改操作时分配
      • 内存中维护事务 id 全局变量，256 倍数时刷新到系统表空间第 5 页的 Max trx ID 属性
    • 聚簇索引行格式 真实数据 中的隐藏信息中记录了 trx_id 即为改动记录的事务对应的 id

    undo log 格式¶

    • undo log 的页类型为 FIL_PAGE_UNDO_LOG File Header
    • 从系统表空间或 undo tablespace 分配
    • 增删改操作只考虑记录聚簇索引上的信息，二级索引可以根据主键来 undo
    • 聚簇索引行格式 真实数据 中的隐藏信息中记录了 roll_pointer 指向对应的 undo log，第一个 bit 代表 update/insert

    INSERT undo log¶

    TRX_UNDO_INSERT_REC

    DELETE undo log¶

    • 删除记录的原理
      • Page Header 中的 PAGE_FREE 是已删除记录的链表
      • 删除的过程分为两阶段
        • delete mark：首先将待删除记录头信息 delete_mask 置 1，所在事务提交之前都称为中间状态 (实现 MVCC)
        • purge：删除所在事务提交后，专门的线程将记录从正常链表移除，从头部插入垃圾链表，调整 Page Header 中的其他属性
      • PAGE_GARBAGE 统计当前页面可重用存储空间，新插入节点只和 PAGE_FREE 的头节点比较大小，页面快满时根据PAGE_GARBAGE进行页内碎片整理

    TRX_UNDO_DEL_MARK_REC

    - 记录 old trx_id & roll_pointer 形成 undo 版本链
    - 索引列信息用于事务提交后的 purge 阶段

    UPDATE undo log¶

    不更新主键¶
    • 就地更新：每个列更新后占用相同的空间
    • 先删除再插入：任何一个列不等大，按照删除流程完全删除旧记录后插入新的
      TRX_UNDO_UPD_EXIST_REC
    • 记录更新列数量和更新前信息
    更新主键¶
    • 涉及到更新主键需要改变记录在聚簇索引中的位置即可能更改页面
    • 更新主键值对聚簇索引的处理 TRX_UNDO_DEL_MARK_REC + TRX_UNDO_INSERT_REC
      • delete mark 旧记录
      • 根据新主键值定位后插入新记录

    undo log 页面¶


    - undo page header 中包含
    - TRX_UNDO_PAGE_TYPE 页面存储 undo log 的种类 分为 TRX_UNDO_INSERT 和 TRX_UNDO_UPDATE 除 INSERT 之外的需要为 MVCC 保留
    - TRX_UNDO_PAGE_START / TRX_UNDO_PAGE_FREE 起始 / 结束偏移量
    - TRX_UNDO_PAGE_NODE 双向链表节点结构

    undo log 链表¶

    • 一个事务可能包含多个操作，填充多个链接成链表的 undo log 页面
    • INSERT / UPDATE 不同类型的 log 需要分开两个链表
    • 普通表 / 临时表 链表也需要分开
    • 对于一个事务，以上 4 个链表是按需分配的
    • 不同事务产生的日志写入不同页面链表中

    undo log 写入¶

    undo log Segment Header¶

    • 每个 undo 链表对应一个段
    • undo log 链表的第一个页面另含 30B Undo Log Segment Header
    • TRX_UNDO_STATE undo 页面链表的状态
      • TRX_UNDO_ACTIVE ：一个活跃事务正在往段里写入 log
      • TRX_UNDO_CACHED ：缓存状态，链表等待被其他事务重用
      • TRX_UNDO_TO_FREE ：insert 链表的事务提交后，该链表不能被重用
      • TRX_UNDO_TO_PURGE ：update 链表的事务提交后，该链表不能被重用
      • TRX_UNDO_PREPARED ：处于 PREPARE 阶段的事务产生的日志
    • TRX_UNDO_LAST_LOG 最后一个 undo log header 位置
    • TRX_UNDO_FSEG_HEADER 本链表对应的 Segment Header 信息，用来定位 INODE Entry
    • TRX_UNDO_PAGE_LIST 链表基节点

    undo log Header¶

    • 同一个事务向一个 undo 链表写入的 log 为一组（链表还可能重用）
    • 需要另一个 header 记录事务相关的属性
      其中包含事务信息、是否包含 delete mark 操作、本组第一条 log、前/后组 undo log 位置、History 链表节点等

    重用 undo 页面¶

    • 条件：链表仅包含一个 undo 页面，已经使用的空间小于 3/4
    • 调整 Undo Page Header、Undo Log Segment Header 的属性
    • 对于 INSERT 链表：覆盖下面的 Undo Log Header 和具体日志
    • 对于 UPDATE 链表：尾部添加新的 Undo Log Header 和具体日志

    回滚段¶

    Rollback Segment Header 页面¶

    • 用于管理 first undo page，每个 Header 对应一个回滚段
    • TRX_RSEG_MAX_SIZE：所有 undo 链表的页面之和最大值
    • TRX_RSEG_HISTORY_SIZE & TRX_RSEG_HISTORY：History 链表页面数 & 基节点
    • TRX_RSEG_FSEG_HEADER：本回滚段对应的 Segment Header
    • TRX_RSEG_UNDO_SLOTS：undo 链表 first undo page 页号集合 (1024 页 * 每页 4B)

    从回滚段申请 undo 链表¶

    • 未分配 undo 页面链表时 undo slots 置为全 1 FIL_NULL
    • 事务分配 undo 链表时依次检查 slots 是否占用，选择一个空的 slot
      • 在表空间中新建一个 undo 链表对应的段 undo log Segment Header， 申请一个页面作为链表 first page，设置 slot 对应页号
      • 若 1024 个 slot 都没有空间则会显式报错 Too many active concurrent transactions
    • 事务提交时处理 slot
      • 指向的 undo 页面链表符合重用条件则重用 undo 页面，将链表undo log Segment Header的状态置为 TRX_UNDO_CACHED 并将 slot 加入回滚段的 insert/update undo cached 链表
      • 不符合重用条件
        • slot 指向 insert undo 链表，则 undo 链表状态置为 TRX_UNDO_TO_FREE 释放 undo 页面链表对应的段，slot 置为空
        • 指向 update undo 链表，则 undo 链表状态置为 TRX_UNDO_PRUGE 将本事务的 undo log 置于 history 链表中，slot 置为空

    多个回滚段¶

    • 定义了 128 个回滚段，共支持128 * 1024 = 131072 个读写事务并发执行
    • 系统表空间第 5 号页面中存储了 128 个指针，通过表空间 ID + 页号指向 Rollback Segment Header 页面
    • 0 号回滚段必须在系统表空间中， 33 - 127 号可以默认在系统或配置 undo 表空间，1-32 号必须在临时表空间且数量固定
    • 修改针对普通表的回滚段中的 undo 页面时，需要记录对应的 redo 日志

    回滚段分配过程¶

    • 首先事务改动普通表前，到系统表空间 5 号页面分配一个回滚段，获取 Rollback Segment Header 页面地址
    • 查看 insert/update undo cached 链表，优先分配缓存的 slot
    • 若没有缓存则依次寻找空 slot
    • 新 slot 需要分配 undo log 段，然后从中申请页面作为 undo 链表首页
    • 写入 undo 页面链表

    通过回滚段进行 undo 恢复¶

    • 保证原子性：redo 将未落盘页面恢复后（包括 undo log 页面），还需要 undo 将未提交事务回滚
    • 崩溃恢复过程
      • 系统表空间 5 号页面找到所有回滚段指针
      • 每个回滚段 undo slot 中寻找存在的 undo 页面链表头页号
      • 从每个 first undo page 中获取状态属性，需要恢复 active 状态的
      • 从首页 undo log segment header 获取链表最后一个 undo log header
      • 进而从 last log 的 undo log header 找到未提交的事务信息进行回滚

    事务隔离与 MVCC¶

    事务隔离级别¶

    • Isolation 隔离性和性能的取舍
    • 事务并发问题
      • 脏写：A 修改另一个未提交事务 B 修改过的数据，若 B 回滚会撤销 A 事务的修改
      • 脏读：A 读到了另一个未提交事务 B 修改过的数据，若 B 回滚 A 相当于读到不存在的数据
      • 不可重复读：A 只能读到另一个已经提交的事务 B 修改过的数据，并且 B 每对该数据进行一次修改并提交后，A 都能查询得到最新值
      • 幻读：A 先根据某些条件查询出一些记录，之后 B 插入了符合条件的记录，A 事务再次按照该条件查询时，能把 B 新插入的也读出来（删除了之前读到的记录属于不可重复读）
    • SQL 标准中的隔离级别
      • READ UNCOMMITTED ：未提交读，不会脏写
      • READ COMMITTED ：已提交读，基础上不会脏读
      • REPEATABLE READ ：可重复读，基础上不会不可重复读，默认
      • SERIALIZABLE ：可串行化，不会发生四种事务并发问题
    • 不同数据库厂商对于隔离级别允许的问题有出入，MySQL 在 REPEATABLE READ 下，可以禁止幻读
    • SET [GLOBAL|SESSION] TRANSACTION ISOLATION LEVEL level;

    MVCC 原理¶

    版本链¶

    • 利用聚簇索引必要的隐藏列 trx_id （事务 id）和 roll_pointer（指向 undo log）
    • insert undo log 只在事务回滚有效，提交事务后 undo 页面链表被释放，与 MVCC 无关
    • 聚簇索引的 roll_pointer ，和 insert undo log 的 old roll_pointer 指向下一个新的 undo log，组成版本链

    ReadView 一致性视图¶

    • READ UNCOMMITTED 下允许脏读，只需要读最新记录
    • SERIALIZABLE 下需要另外加锁实现串行化
    • 中间两个隔离级别 READ COMMITTED 和 REPEATABLE READ 需要保证不会脏读，即读取已提交的事务修改的记录
    • ReadView 保存的信息
      • m_ids ：生成 ReadView 时系统中活跃的读写事务的事务 id 列表
      • min_trx_id ：生成 ReadView 时系统中活跃的读写事务中最小的事务 id，m_ids 中的最小值
      • max_trx_id ：生成 ReadView 时系统中应该分配给下一个事务的 id 值
      • creator_trx_id：生成该 ReadView 的事务的 id
    • 使用 ReadView 判断某个版本是否可见
      • m_ids 列表包含当前检查版本的事务 id，即当前该事务还在活跃，则不可见
        • 被访问版本的 trx_id 在 ReadView 的 min_trx_id 和 max_trx_id 之间，需要判断 trx_id 是否在 m_ids 列表中。若在，说明创建 ReadView 时生成该版本的事务还是活跃的，该版本不可以被访问；如果不在，说明创建 ReadView 时生成该版本的事务已经被提交，该版本可以被访问
      • 使用creator_trx_id min_trx_id max_trx_id可以加速判断
        • 被访问版本的 trx_id 与 ReadView 中的 creator_trx_id 相同，当前事务在访问自己修改过的记录，该版本可以被当前事务访问
        • 被访问版本的 trx_id 小于 ReadView 中的 min_trx_id 值，生成该版本的事务在当前事务生成 ReadView 前提交，该版本可以被当前事务访问
        • 被访问版本的 trx_id 大于 ReadView 中的 max_trx_id 值，生成该版本的事务在当前事务生成 ReadView 后才开启，该版本不可以被当前事务访问
    • 读取记录的事务可以沿版本链查询最新的可见版本

    不同隔离级别生成 ReadView 时机¶

    • READ COMMITTED 的事务每次读取数据生成一个 ReadView
    • REPEATABLE READ 的事务第一次读取数据生成一个 ReadView
      • 保证了读事务的可重复读
      • START TRANSACTION WITH CONSISTENT SNAPSHOT 可以立刻生成这个 ReadView
      • 使用一致性非锁定读（快照读） 符合条件多条记录，其他事务插入并提交符合条件的记录，新记录版本对读事务不可见，避免快照读下的幻读
      • 使用锁定读（当前读）还需要 next-key lock 避免幻读

    二级索引利用 MVCC¶

    • 二级索引记录中没有 trx_id 和 roll_pointer
    • 二级索引页面 Page Header 中有 PAGE_MAX_TRX_ID ，若修改页面记录的事务 id 大于旧属性值，则设置属性为当前事务 id
    • 若查询语句通过二级索引进行查询
      • 检查 ReadView 中 min_trx_id 是否大于该页面的PAGE_MAX_TRX_ID，若是则记录可见，否则需要回表查询
      • 若进行了回表查询，首先找到对当前 ReadView 可见的最新版本，然后判断查询列的值是否相同

    Purge 操作¶

    • ReadView 结构连接成链表，还包含当前最大的事务 no + 1 作为编号
    • 事务提交时会分配事务 no 提交顺序编号
    • purge 操作取出最早的 ReadView，从各个回滚段 Rollback Segment Header 页面 的 History 链表中取出事务提交过的 undo log
    • 如果一组提交过的 undo log 的事务 no 小于当前系统最早生成的 ReadView 的事务 no，说明 undo log 不会再用到
    • 从 history 链表移除，释放 log 存储空间，删除进行过 delete mark 的 undo log 对应的真实记录
    • 使用 RR 隔离级别的事务运行时间很长会让 ReadView 一直复用，从而导致版本链变长

    锁¶

    • 写-写情景加锁避免脏写
    • 对于读-写情景出现的脏读、不可重复读、幻读
      • 读操作使用 MVCC （RC 避免脏读 RR 避免不可重复读和部分幻读），写操作加锁。读可用版本，写最新版本不冲突
      • 或者舍弃一部分性能读写均加锁
    • 一致性无锁定读（快照读）：普通的 SELECT 在 RC 或 RR 隔离级别下不会对任何记录加锁
    • 锁定读：
      • SELECT ... LOCK IN SHARE MODE 使用 Shared lock 锁定读取的记录
      • SELECT ... FOR UPDATE 使用 Exclusive lock
    • 写操作：
      • DELETE：定位记录后获取 X 锁后进行 delete mark
      • UPDATE：参考 UPDATE undo log
        • 不修改主键且原地修改：定位记录获取 X 锁后修改
        • 不修改主键但列不等大：定位记录获取 X 锁后进行完整删除流程再插入记录，锁转移到新记录
        • 修改主键：按 DELETE + INSERT 操作分解
      • INSERT：一般插入记录受隐式锁保护

    多粒度锁¶

    • 表级 S X 锁需要检查是否有不兼容的行级锁
    • 表级意向锁 Intention Lock IS & IX
      • 意向锁全部互相兼容
      • 行 S / X 锁，先添加表级 IS / IX 锁
      • 表 S / X 锁，检查是否有 IX / IS&IX 锁再上锁

    InnoDB 的锁¶

    • 表级锁
      • 一般情况不使用表级 SX 锁，对表使用 DDL 语句涉及 server 层元数据锁
      • IS / IX 锁
      • AUTO-INC 锁：作用范围单个语句 innodb_autoinc_lock_mode调整模式
        • 获取表级 AUTO-INC 锁为每条待插入记录分配递增值，阻塞其他事务插入，语句执行结束后才释放
        • 或者插入数量确定情况下采用轻量级锁生成值
        • 由于范围是单个语句，事务回滚会导致自增不连续
    • 行级锁
      • Record Lock S / X
      • Gap Lock 防止向一条记录前的空隙插入幻影记录，gap 之间不互斥
      • Next-key Lock 锁住当前记录以及记录前空隙 = gap 锁 + 记录锁
      • Insert Intention Lock 为等待 gap 锁生成的锁
      • 隐式锁
        • 当一个事务插入记录后另一个事务立刻锁定读 / 修改这条记录，会出现脏读 / 脏写现象
        • 对聚簇索引记录，事务添加行锁前检查 trx_id 是否为活跃事务，若是则帮助当前事务创建 X 锁，再给自己创建等待中的锁
        • 对二级索引可以检查 Page Header 的 PAGE_MAX_TRX_ID ，如果不小于最小的活跃事务，还需要回表查询 trx_id
        • 起到延迟生成锁的效果

    锁的内存结构¶


    - n_bit 结构末尾 bit 长度
    - type_mode 32 位锁类型信息
    - lock_mode 4bit 区分 S/X/IS/IX/AUTO-INC
    - lock_type 4bit 区分表 / 行级
    - rec_lock_type 24bit 细分行级锁类型 + LOCK_WAIT 标志位
    - 末尾比特位标记 记录头信息的heap_no

    语句加锁分析¶

    普通 SELECT 语句¶

    • 除了 SERIALIZABLE 都不加锁
    • RR 下很大程度避免幻读，而不是完全避免
      • T1 查询，T2 插入并提交，（ReadView 允许 T1 修改 T2 插入的新数据即trx_id 变为 T1 ，T1 此时再查询）或者 （T1 直接锁定读），新数据版本对同事务可见，发生幻读
      • 对于锁定读（当前读）无法解决幻读
    • SERIALIZABLE 加锁
      • 系统变量 autocommit=0 时 普通查询转换为 S 锁定读
      • 启动自动提交每个事务仅单个语句，MVCC 生成一个 ReadView，无需考虑不可重复读和幻读

    锁定读语句¶

    • 两种锁定读以及 UPDATE DELETE 的定位过程都可以看作锁定读
    • 读取扫描区间步骤
      1. 定位区间第一条记录
      2. 为当前记录加锁，一般不大于 RC 隔离级别则加记录锁，不小于 RR 则加 next-key 锁
      3. 判断索引条件下推是否成立（仅适用于二级索引和 SELECT）
        • 若不符合获取下一条记录重新开始
        • 同时判断边界条件，若不符合则向 server 返回查询完毕
      4. 若读取二级索引则执行回表，给聚簇索引加锁
      5. 判断边界条件，若不符合向 server 返回查询完毕，不大于 RC 还要释放该记录的锁
      6. server 层判断其他条件是否成立，发送给客户端。不成立且不大于 RC 还要释放锁
      7. 获取下一条记录回到步骤 2 加锁
    • RR / RC 区别
      • 扫描的当前记录加锁类型（是否要考虑防止 gap 插入）
      • 边界条件不符合时是否释放锁
      • server 层其他条件不成立时是否释放锁
    锁定读总结¶
    • RR 级别下
    • 匹配模式为精确匹配
      • 唯一索引：记录存在则记录锁，不存在则间隙锁
      • 非唯一索引：记录存在则 next-key 锁 + 不符合条件的第一条 gap 锁，不存在则下一条 gap 锁
    • 非精确匹配（范围查询）
      • 唯一索引
        • 左开区间（大于）：从第一个不符合的开始加 next-key
        • 左闭区间（大于等于）：若左闭条件记录存在则退化成记录锁
        • 右开区间（小于）：最后一条退化 gap 锁
        • 右闭区间（小于等于）：条件值记录存在则该记录的锁不会退化
      • 非唯一索引
        • 由于字段可以重复，next-key 不会退化以防幻读

    INSERT 语句¶

    • 一般情况下使用隐式锁保护新插入的记录
    • 定位插入位置遇到 gap 锁会生成意向锁并等待
    • 特殊情况
      • 遇到重复主键报错前给聚簇索引记录加 S 锁
      • 重复唯一二级索引报错前给二级索引记录加 S next-key 锁
      • INSERT ... ON DUPLICATE KEY ... 加 X 锁

    死锁¶

    • 互斥、占有且等待、不可强占用、循环等待
    • 开启 InnoDB 检测机制 innodb_deadlock_detect 自动回滚影响较小的事务
    • 设置事务等待锁的超时时间 innodb_lock_wait_timeout
