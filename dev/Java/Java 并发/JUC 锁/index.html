    JUC 锁

    锁分类¶

    乐观锁 / 悲观锁¶

    • 访问数据 认为不会竞争：不加锁 vs 认为会竞争：提前加锁
    • 乐观锁实现：volatile & synchronized + 自旋重试
    • 适合不同的读 / 写场景

    无锁 偏向锁 轻量级锁 重量级锁¶

    针对 volatile & synchronized

    可重入锁 / 不可重入锁¶

    • 可重入锁又名递归锁，指同一个线程在外层方法获取锁的时候，再进入该线程的内层方法会自动获取锁（锁的是同一个对象或者类）
    • ReentrantLock 和 synchronized 是可重入的
    • 可重入锁一定程度避免出现死锁，获取内层锁时不会因为需要释放外层而死锁
    • 可重入锁获取时判断当前线程是否已经获取锁，释放时 status - release == 0 才会释放

    公平锁 / 非公平锁¶

    • 是否实现获取锁的 FIFO
    • 非公平锁能提升一定的效率，但可能会发生线程饥饿
    • ReentrantLock 支持非公平锁和公平锁，synchronized 是非公平锁

    读写锁 / 排他锁¶

    • ReentrantLock 和 synchronized 是排他锁，同一时刻只允许一个线程访问
    • 读写锁在同一时刻允许多个读线程访问
    • 共享 / 排他通过 AQS 实现

    可中断锁 / 不可中断锁¶

    • 获取锁的过程中可以被中断（放弃获取） / 等到获取锁之后才进行中断处理
    • synchronized 是不可中断锁
    • ReentrantLock 提供了两种实现
      • lockInterruptibly() 可中断，使用 AQS 的 doAcquireInterruptibly()，自旋遇到中断即抛异常
      • lock() 不可中断，使用 AQS 的 doAcquire()，遇到中断进行标记，获取后再处理

    JUC 锁¶

    synchronized的不足
    - 如果临界区是只读操作，可以多线程执行，但使用 synchronized 的话，同一时间只能有一个线程执行
    - synchronized 无法知道线程有没有成功获取到锁
    - 使用 synchronized，如果临界区因为 IO 或者 sleep 方法等原因阻塞了，而当前线程又没有释放锁，就会导致所有线程等待

    抽象类 AQS¶

    • AQS 是队列同步器的基本实现

    接口¶

    • locks 包有三个接口：Condition、Lock、ReadWriteLock
      • Lock 接口包含获取锁和释放锁的方法声明，以及获取 Condition 的方法声明

    锁类¶

    • ReentrantLock 可重入锁
    • ReentrantReadWriteLock 读写锁
    • StampedLock 性能更好的读写锁

    工具类¶

    • Semaphore 计数信号量
    • CountDownLatch 控制线程等待
    • CyclicBarrier 可循环使用的屏障
    • Exchanger 线程间数据交换
    • Phaser 多线程同时完成任务

    ReentrantLock¶

    源码分析¶

    • 包含继承 AQS 的抽象内部类 Sync，有两个子类实现 FairSync 和 NonfairSync

    • 默认使用非公平锁，可以通过构造器来显式的指定使用公平锁

    • 非公平获取资源

      • 判断 state 是否被占有，若资源空闲则尝试 CAS 获取，设置独占持有者
      • 若被占有，是同一线程重入则计数更新 state

    • 公平获取资源

      • 资源空闲同时还需要通过 hasQueuedPredecessors() 判断无前驱节点等待才能获取

    • 释放资源

      • 计算更新后的 state，且保证持有者是当前线程
      • 更新后的 state 为 0，表示成功释放锁，独占持有者置为 null
      • 更新state

    使用 ReentrantLock¶

    • ReentrantLock 必须在 finally 中手动释放，确保锁无论在正常情况下还是异常情况下都能被释放
    • 锁必须在 try 代码块开始之前获取，并且加锁之前不能有异常抛出，否则在 finally 块中就无法释放锁
      Lock lock = new XxxLock();
// ...
lock.lock();
try {
    doSomething();
    doOthers();
} finally {
    lock.unlock();
}

    ReentrantLock vs. synchronized¶

    • 类 / 关键字
    • 多路选择通知 / 单路通知（唤醒一个或全部线程）
    • 手动 / 自动释放锁
    • synchronized 在现代 JDK 版本得到优化（锁升级、锁消除、锁粗化等）

    ReentrantReadWriteLock¶


    - 实现了 ReadWriteLock 接口， 也实现了FairSync 和 NonfairSync，外加读写锁
    - AQS 的 state 被分为高/低16位分别为读/写状态
    - 有读锁或写锁已经被其他线程获取，写锁获取失败
    - 当写锁被其他线程获取后，读锁获取失败
    - 锁降级：获取写锁、写数据、获取读锁、释放写锁
    - 锁无法升级，写锁会竞争，且两个读锁同时升级会死锁

    StampedLock¶

    • JDK 1.8 引入的性能更好的读写锁，不可重入且不支持条件变量 Condition
    • 不实现现有接口而是基于 CLH 锁独立实现
    • 不可重入读写锁 + 乐观读（允许多个线程获取乐观读以及读锁。同时允许一个写线程获取写锁）

    Condition 接口¶


    - 通过lock.newCondition() 创建 ConditionObject对象，是 AQS 的内部类
    - 内部维护 FIFO 单向队列，调用 await() 的线程加入该队列，线程处在 Waiting，AQS Node waitStatus 为 CONDITION
    - Lock 可以创建多个 ConditionObject，持有多个等待队列；Object 中的方法只能使用一套 moniter 的队列

    主要方法¶

    • await()：线程等待直到被通知或者中断。类似 Object.wait()
    • awaitUninterruptibly()：线程等待直到被通知，即使在等待时被中断也不会返回。没有与之对应的 Object 方法
    • await(long time, TimeUnit unit)：线程等待指定的时间，或被通知，或被中断。类似 Object.wait(long timeout)，提供了更灵活的时间单位
    • awaitNanos(long nanosTimeout)：线程等待指定的纳秒时间，或被通知，或被中断。没有与之对应的 Object 方法
    • awaitUntil(Date deadline)：线程等待直到指定的截止日期，或被通知，或被中断。没有与之对应的 Object 方法
    • signal()：唤醒一个等待的线程。类似 Object.notify()
    • signalAll()：唤醒所有等待的线程。类似 Object.notifyAll()

    源码分析¶

    await¶

    • 当前线程包装成 Node，waitStatus = CONDITION，尾插等待队列
    • 释放当前线程的锁并唤醒下个节点
    • 进入循环，确认当前线程从同步队移除后使用LockSupport.park(this)进入 Waiting 状态
      • 被中断 break 或 Condition.signal() 移到同步队列才能出循环
    • 调用acquireQueued(node, savedState)自旋获取到资源，即获取到 Condition 关联的 lock
    • 处理中断的抛出

    awaitUninterruptibly¶

    • 区别在于线程等待不受中断影响，获取资源后再处理中断

    signal¶

    • 检查是否获取了锁
    • 获取等待队列中头节点即等待时间最长的节点
    • 将头节点 waitStatus CAS 从 -2 CONDITION 置为 0（默认）
    • 自旋 CAS 插入同步队列尾部

    LockSupport¶

    • 以线程为操作对象
    • 基于 Unsafe 类的 park / unpark
    • unpark 的语义为“使线程持有许可证”，park 的语义为“消费线程持有的许可”，没有严格的执行顺序
    • 不会竞争锁对象产生死锁问题
    • LockSupport.park() 的等待是可以被中断的，但不会抛出 InterruptedException，park 后需要自行判断线程中断
