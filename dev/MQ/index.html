    RabbitMQ¶

    安装¶

    docker安装Rabbitmq教程

    基础¶

    • MQ：一种具有接收数据、存储数据、发送数据等功能的技术服务。参与消息传递的双方称为 生产者 和 消费者 ，生产者负责发送消息，消费者负责处理消息。

    作用¶

    • 异步处理
      请求中包含的耗时操作通过消息队列实现异步处理，减少响应时间，提高用户体验
    • 削峰限流
      将短时间高并发产生的事务消息存储在消息队列中，然后后端服务再根据自己的能力去消费消息
    • 降低系统耦合性
    • 分布式事务
    • 延时定时处理

    问题¶

    • 系统可用性降低：系统可用性在某种程度上降低，需要考虑消息丢失或者说 MQ 挂掉等情况
    • 系统复杂性提高：需要保证消息没有被重复消费、处理消息丢失的情况、保证消息传递的顺序性等问题
    • 一致性问题：消息的真正消费者并没有正确消费消息

    RabbitMQ 基本概念¶

    • 消息
      消息头 (Label) 和消息体 (payLoad)。消息体是不透明的，而消息头则由一系列的可选属性组成，这些属性包括 routing-key（路由键）、priority（相对于其他消息的优先权）、delivery-mode（指出该消息可能需要持久性存储）等。生产者把消息交由 RabbitMQ 后，RabbitMQ 会根据消息头把消息发送给感兴趣的 Consumer
    • Exchange
      • 接收生产者发送的消息并将这些消息路由给服务器中的队列中。如果路由不到，返回给 Producer 或直接丢弃掉
      • 生产者将消息发给交换器的时候，一般会指定一个 RoutingKey，用来指定这个消息的路由规则
      • 通过 Binding 将 Exchange 与 Queue 关联起来（多对多），在绑定的时候一般指定一个 **BindingKey
      • direct(默认) 消息路由到 Bindingkey 与 RoutingKey 完全匹配的 Queue
      • fanout 所有绑定 Queue
      • topic Bindingkey 中可以用 * 和 # 模糊匹配
      • headers 完全匹配消息 headers 性能差
    • Queue
      • 用来保存消息直到发送给消费者
      • 多个消费者可以订阅同一个队列，这时队列中的消息会被轮询平摊给多个消费者
      • 不支持队列层面的广播消费
    • Broker
      看作服务节点或服务器

    消息可靠性¶

    Publisher - Broker 丢失¶

    • 事务消息是阻塞性的，对性能影响大，引入确认机制
    • 开启生产者确认机制 confirmCallback 保证消息到达 Broker
      spring:
    rabbitmq:   
        # 开启 confirm 确认机制
        publisher-confirm-type: correlated
    • 消息被 Broker 接收即执行 confirmCallback，集群模式下需要所有 broker 接收到
      final RabbitTemplate.ConfirmCallback confirmCallback = (CorrelationData correlationData, boolean ack, String cause) -> {
            log.info("correlationData: " + correlationData);
            log.info("ack: " + ack);
            if(!ack) {
                log.info("异常处理....");
            }
    };
rabbitTemplate.setConfirmCallback(confirmCallback);

      CorrelationData：用来表示当前消息唯一性 id
      ack：是否成功
      cause：失败原因
      CorrelationData 主要用于 ConfirmCallback 中的消息确认，并未直接绑定到 ReturnsCallback 的 MessageProperties 中

    Exchange - Queue 丢失¶

    • 对于不可路由的消息，有两种处理方式：Return 消息机制和备份交换机
    • 开启可靠抵达 returnCallback 保证消息投递到目标队列
    • 注意不要被代码配置的Bean覆盖
      spring:
    rabbitmq:
        # 触发ReturnCallback必须设置mandatory=true, 否则Exchange没有找到Queue就会丢弃掉消息, 而不会触发ReturnCallback
        template.mandatory: true
        publisher-returns: true
    • 只要消息没有投递给指定队列触发失败回调
      rabbitTemplate.setReturnsCallback(returnedMessage -> {  
    // 设置消息错误状态  
    redisMessageStore.updateMessageFailed(returnedMessage.getMessage().getMessageProperties().getCorrelationId());  
    log.info("Fail Message[{}]==>replyCode[{}]==>replyText[{}]==>exchange[{}]==>routingKey[{}]",  
            returnedMessage.getMessage(), returnedMessage.getReplyCode(), returnedMessage.getReplyText(), returnedMessage.getExchange(), returnedMessage.getRoutingKey());  
});

      需要在发送消息时配置message.getMessageProperties().setCorrelationId(correlationId);否则 getCorrelationId 获取不到 uuid
    • 备份交换机 alternate-exchange 是普通 exchange，发送消息没有匹配到 queue，就会自动转移到备份交换机对应的 queue，消息不会丢失

    Queue - Consumer 丢失¶

    • 消费者收到消息还没来得及处理就宕机，消息者默认采用自动 ack，一旦消费者收到消息后会通知 MQ Server 已经处理好了，MQ 就会移除这条消息，导致消息丢失
    • 消费者手动确认机制
      ##设置消费端手动 ack
spring:
    rabbitmq:
        listener.simple.acknowledge-mode: manual
    • 消费者处理完逻辑之后再回复ack，表示消息已经成功消费可以删除。当消息者消费失败的时候，给 broker 回复 nack，根据配置决定重新入队还是从broker移除，或者进入死信队列
    • 没收到 ack，broker 会认为消息正在处理，不会 requeue，也不会分配给其他消费者
    • 感知到客户端断开，无 ack 的消息会被 requeue 进入 ready 状态
      @RabbitListener(queues = RabbitMqConfig.MAIL_QUEUE)
public void onMessage(Message message, Channel channel) throws IOException {
    // 处理消息...
    long deliveryTag = message.getMessageProperties().getDeliveryTag();
    // 手动ack，第二个参数multiple 设置为true表示序列号及之前的消息都已经收到，设为false则表示收到本条消息
    try {
        channel.basicAck(deliveryTag, false);
        System.out.println("mail listener receive: " + new String(message.getBody()));
    } catch (Exception e) {
       // 网络中断 
    }
}

      basicNack 否定确认，可以指定 broker 是否 requeue 消息，可以批量
      basicReject 否定确认，不能批量

    消息 TTL¶

    • 队列和消息均可设置 TTL
    • 消息 TTL 指的是一条消息在队列中可以存活的最大时间
    • 通过设置消息属性中的 expiration 或通过队列属性中的 x-message-ttl 来配置
    • 通过设置队列的 x-dead-letter-exchange 或 x-dead-letter-routing-key，过期的消息可以被转发到指定的死信队列

    死信路由 Dead Letter Exchanges¶

    进入死信路由条件¶

    • 被消费者拒收且不 requeuebasic.reject or basic.nack with requeue parameter set to false
    • 消息 TTL 到期
    • 达到队列长度限制
      队列过期不会让消息成为死信
      死信路由是一种普通的 Exchange

    SpringBoot 整合 RabbitMQ¶

    • 属性在 spring.rabbitmq 下读取，主要配置 host port virtual-host 等
    • 配置
    • @EnableRabbit

    配置 MQ¶

    • AmqpAdmin 配置
    • @Configuration @Bean 注入
      • MessageConverter 注意 LocalDateTime 问题
      • Exchange TopicExchange(String name, boolean durable, boolean autoDelete, Map<String, Object> arguments)
      • Queue Queue(String name, boolean durable, boolean exclusive, boolean autoDelete, Map<String, Object> arguments)
      • Binding Binding(String destination, DestinationType destinationType, String exchange, String routingKey, Map<String, Object> arguments)
        为了不覆盖 RabbitAutoConfiguration 自动配置的 template 按照如下自定义 converter 和成功/失败回调函数
        @Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory, RabbitTemplateConfigurer configurer) {
    RabbitTemplate rabbitTemplate = new RabbitTemplate(connectionFactory);
    configurer.configure(rabbitTemplate, connectionFactory);
    rabbitTemplate.setMessageConverter(messageConverter());
    //确认回调
    rabbitTemplate.setConfirmCallback((correlationData,ack,cause) -> {
        log.info("confirm...correlationData[{}]==>ack:[{}]==>cause:[{}]", correlationData, ack, cause);
    });
    //失败回调
    rabbitTemplate.setReturnsCallback(returnedMessage -> {
        // 设置消息错误状态
        redisMessageStore.updateMessageFailed(returnedMessage.getMessage().getMessageProperties().getCorrelationId());
        log.info("Fail Message[{}]==>replyCode[{}]==>replyText[{}]==>exchange[{}]==>routingKey[{}]",
                returnedMessage.getMessage(), returnedMessage.getReplyCode(), returnedMessage.getReplyText(), returnedMessage.getExchange(), returnedMessage.getRoutingKey());
    });
    return rabbitTemplate;
}

    消息重复¶

    • 消息消费失败 reject 后重试
    • 消息消费成功 ACK 时宕机，Broker 消息 ready 重发
      • 消费接口业务中对状态进行判断，设计成幂等的
      • 使用防重表
      • 消息属性 redelivered 区分消息是否为重试

    消息积压¶

    • 消费者宕机
    • 消费者消费能力不足
    • 发送者流量过大
      上线更多消费者 / 上线另外的消费者服务，先批量消费消息尽快落库然后离线处理

    扩展¶

    Classic Queue Storage Impl.¶

    • Before 3.10: journal & segment file 读取消息加载整个 file 到内存，内存压力 I/O负担影响性能
    • After 3.10-3.12: Load when necessary 基于消费速率改变
    • 仍然存在消息积压，适合用于数据量小且稳定的业务场景

    Quorum Queue 仲裁队列¶

    • 未来可能代替传统队列
    • 基于 Raft 协议
    • 容错 / 安全 > 低延迟 要求，适合订单等
    • 队列消息积压严重不建议使用

    Stream 流式¶

    • 3.9.0 引入的新式队列类型
    • 使用 append-only 日志记录消息，调整消费者 offset 实现消息分发，没有入队出队
    • 适用场景
      • 多个消费者的大分发
      • 回溯历史消息
      • 大吞吐量
      • 允许大规模消息积压
    • 消息安全性：不显式 flush 到存储 依赖 OS 非正常关机带来风险

    Sharding 插件¶

    • 配置 policy，Producer 指定虚拟交换机，尽量均匀发送消息到分片队列
    • 消费者指定虚拟队列 = 交换机名
    • 产生乱序接收
    • 尽量不要单独消费某个分片队列
